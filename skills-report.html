engineering（18 個）

日常寫程式使用的 skills。串成一條主流程：/grill-with-docs 磨利想法 → 需要時繞道 /prototype → 大工作走 /to-spec → /to-tickets → 每張 ticket 用 /implement（內部驅動 /tdd，收尾跑 /code-review）。

ask-mattUSER-INVOKED整個倉庫的路由器：告訴你該用哪個 skill / flow

用途

當使用者不確定該用哪個 skill 或流程時，ask-matt 提供一張完整的地圖：主流程（idea → ship）、入口流程（on-ramps）、獨立工具，以及各階段之間如何銜接。

觸發時機

使用者想問「我的情況該用哪個 skill / flow」時手動觸發。

工作流程 / 特色

  • 定義主流程：/grill-with-docs → 繞道 /prototype → /to-spec → /to-tickets → /implement → /code-review。
  • 強調 context hygiene：注意約 150k tokens 的「smart zone」上限，必要時在階段邊界 /compact。
  • On-ramps：issue 堆積走 /triage；東西壞了走 /diagnosing-bugs；超大模糊工程走 /wayfinder。
  • 附 PHASE-BOUNDARIES.md：定義階段邊界處五個選項（Continue、/clear、/handoff、Subagent、/compact）的決策樹。
明確指出 /setup-matt-pocock-skills 是使用其他 engineering skills 的前置條件。
code-reviewMODEL-INVOKED對 diff 做「標準 + 規格」雙軸審查

用途

對「某固定點以來的 diff」做雙軸審查：Standards（是否符合 repo 編碼標準，外加固定的 Fowler 壞味道基線）與 Spec（是否忠實實作原始 issue/spec）。兩軸以併行 sub-agents 執行，結果並列呈現、互不排名。

觸發時機

使用者想審查 branch、PR、進行中的修改，或說「review since X」；也是 /implement 的收尾步驟。

工作流程 / 特色

  • 先釘住 fixed point（git diff <point>...HEAD 三點式），spawn sub-agents 之前先驗證 ref 存在且 diff 非空。
  • 依序找 spec 來源（commit 訊息 → 使用者給的路徑 → docs//specs//.scratch/ → 問使用者）與 standards 來源。
  • Standards 軸永遠帶 12 個 Fowler 壞味道基線；repo 明文標準優先，工具已強制執行的直接跳過。
  • 兩個 sub-agents 併行，聚合時不合併、不重排名，只各軸總結最嚴重問題。
分開兩軸是為了防止「全守規矩但做錯事」或「做對事但壞了慣例」被互相掩蓋。
codebase-designMODEL-INVOKEDdeep modules 設計的共享詞彙與原則參考

用途

設計「deep modules」的共享詞彙與原則參考：module、interface、depth、seam、adapter、leverage、locality。目標是大量行為藏在小介面後面、位於乾淨的 seam 上、可透過介面測試。

觸發時機

使用者想設計或改善模組介面、找 deepening 機會、決定 seam 位置；或另一個 skill 需要這套詞彙時（/tdd、/improve-codebase-architecture 都說這套語言）。

工作流程 / 特色

  • 嚴格詞彙表，明確禁用 component/service/API/boundary 等替代詞。
  • 核心原則：depth 是介面的屬性而非實作；deletion test；介面即測試面；一個 adapter = 假想的 seam，兩個才是真的。
  • 可測性設計三招：接受依賴而非自行建立、回傳結果而非副作用、小表面積。
  • 附 DEEPENING.md 與 DESIGN-IT-TWICE.md（併行 sub-agents 以數種截然不同的方式設計介面再比較）。
明確拒絕 Ousterhout 的「實作行數/介面行數比」定義，改用 depth-as-leverage；這是參考文件而非要跑的 session。
diagnosing-bugsMODEL-INVOKED難 bug 與效能退化的紀律化診斷迴圈

用途

核心信念：先有「一條已跑過、能對這個 bug 變紅的緊密 feedback loop」，之後的一切（最小化、假設、插樁、修復、回歸測試）都是機械操作。

觸發時機

使用者說「diagnose / debug this」，或回報東西壞了、throwing、failing、變慢。

工作流程 / 特色

  • Phase 1 建 feedback loop（skill 本體）：依序嘗試失敗測試、curl 腳本、CLI fixture、headless browser、bisection、differential loop 等，沒有 red-capable 指令就不准進 Phase 2。
  • Phase 2 重現 + 最小化；Phase 3 先列 3–5 個可證偽的排序假設再測；Phase 4 一次只改一個變數插樁，debug log 加 [DEBUG-xxxx] 前綴。
  • Phase 5 先寫回歸測試再修——但只在有「正確 seam」時；沒有正確 seam 本身就是架構發現。
  • Phase 6 清理插樁、寫 post-mortem，必要時移交 /improve-codebase-architecture。
  • 全程必須 redact 秘密（<REDACTED>）。
明確禁止「還沒有 loop 就讀程式建立理論」——這正是本 skill 要防的失敗模式。
domain-modelingMODEL-INVOKED建立並磨利領域模型，即時維護 CONTEXT.md 與 ADR

用途

主動建立並磨利專案的領域模型：挑戰模糊術語、用具體情境壓力測試概念邊界、與程式碼交叉核對，並在術語確定的當下即時更新 CONTEXT.md（glossary）與 ADR。

觸發時機

討論 codebase 術語、撰寫/編輯 CONTEXT.md、記錄或編輯 ADR 時；也被 /grill-with-docs、/triage、/wayfinder、/improve-codebase-architecture 內部驅動。

工作流程 / 特色

  • 檔案布局：單 context 用根目錄 CONTEXT.md + docs/adr/；多 context 用 CONTEXT-MAP.md；檔案 lazy 建立。
  • 四個 session 中的動作：挑戰衝突用法、sharpen 模糊詞、發明邊界情境壓力測試、與程式碼交叉核對。
  • 術語一解決就更新 CONTEXT.md，不批次累積；CONTEXT.md 只能是 glossary，嚴禁實作細節。
  • ADR 要節制：同時滿足「難以逆轉」「沒上下文會讓人困惑」「是真正的 trade-off」三條件才提議。
grill-with-docsUSER-INVOKED主流程第一步：無情訪談磨利想法，同時把知識寫成文件

用途

以無情的訪談（grilling）磨利一個計畫或設計，同時把過程中產生的領域知識寫成文件（glossary、ADR）。SKILL.md 本身只有一行程式：執行 /grilling session 並使用 /domain-modeling skill——是兩個底層 skill 的有狀態包裝。

觸發時機

在 working directory（有 repo）裡想釐清一個想法、計畫或設計時。若不在 repo 中則改用無狀態的 /grill-me。

工作流程 / 特色

  • 底層執行 /grilling：以 design tree + rounds + frontier 的方式逐輪提問。
  • 同時驅動 /domain-modeling：把訪談中確定的術語即時寫進 CONTEXT.md，重要決策記為 ADR。
  • 與 /grill-me 的差異在於「留下紙本紀錄」——在有 repo 時它是嚴格較優的選擇。
implementUSER-INVOKED依 spec / tickets 把功能建出來的標準建置迴圈

用途

依據 spec 或一組 tickets 實際把功能建出來。內部在預先約定的 seams 驅動 /tdd，收尾跑 /code-review，最後 commit 到當前分支。

觸發時機

拿到 spec/ticket 後手動觸發；每張 ticket 通常開一個 fresh session 各自執行。

工作流程 / 特色

  • 盡可能用 /tdd、在 pre-agreed seams 上測試先行。
  • 定期跑 typechecking 與單一測試檔，完整測試套件只在最後跑一次。
  • 完成後用 /code-review 做雙軸審查再 commit。
刻意極簡（SKILL.md 僅 15 行）——只是把 tdd、code-review、commit 串成一個標準建置迴圈的薄編排層。
improve-codebase-architectureUSER-INVOKED掃描程式庫找出 deepening opportunities，產出視覺化 HTML 報告

用途

掃描程式庫找出「deepening opportunities」——把 shallow module 加深為 deep module 的重構候選，以視覺化 HTML 報告呈現，使用者挑一個後進入 grilling 迴圈討論。目標是 testability 與 AI-navigability。

觸發時機

有空檔想改善程式庫架構健康時手動觸發；也是 /diagnosing-bugs post-mortem 發現「沒有好的 seam 可以鎖住 bug」時的移交對象。

工作流程 / 特色

  • 先定範圍再掃描（YAGNI）：優先看近期 commit 熱點；先讀 CONTEXT.md 與相關 ADR。
  • spawn sub-agent 有機探索，尋找 shallow module、缺乏 locality 的純函式、跨 seam 洩漏的耦合等。
  • 產出自包含 HTML 報告（Tailwind + Mermaid via CDN），每個候選有 before/after 圖、Strong/Worth exploring/Speculative 徽章與 Top recommendation。
  • 使用者挑選後跑 /grilling 走決策樹，過程中用 /domain-modeling 即時更新 CONTEXT.md/ADR。
只提出候選、不直接設計介面；候選若抵觸現有 ADR 要明確標示「值得重開」而非默默列出。
prototypeMODEL-INVOKED用 throwaway code 回答一個設計問題

用途

用 throwaway code 回答一個設計問題：邏輯/狀態模型問題產出一個可分享、非工程師也能操作的單一 HTML 檔；UI 問題產出同一路由上多個可用 URL 參數切換的候選版本。

觸發時機

使用者想 sanity-check 狀態模型或邏輯「感覺對不對」、或探索 UI 該長什麼樣；也是主流程 step 2 的繞道。

工作流程 / 特色

  • 先分流：「邏輯/狀態對嗎」→ LOGIC.md；「該長什麼樣」→ UI.md。分流錯誤等於浪費整個 prototype。
  • 共同規則：throwaway 且明確標記、放在將來真正使用的程式碼附近；一條指令即可啟動；預設無持久化；不寫測試不做 polish。
  • 完成後把驗證過的決策折回正式程式碼，prototype 本體作為 primary source commit 到 prototype/<name> 分支（不進 main）。
「Throwaway」是對寫法的約束，不是一定要銷毀——答案是資產，prototype 本體留作可引用的決策證據。
researchMODEL-INVOKED把閱讀型調查委派給背景 agent，產出附引用的 Markdown

用途

針對一個問題查高信任度的 primary sources（官方文件、原始碼、規格、first-party API），產出一份附引用的 Markdown 檔存進 repo，主線工作可以繼續。

觸發時機

使用者想研究某主題、蒐集文件或 API 事實、或把閱讀雜務交給背景 agent。

工作流程 / 特色

  • 以背景 agent 執行，使用者同時繼續手邊工作。
  • 每個 claim 都追溯到擁有它的源頭，不用二手轉述；逐條引用來源。
  • 產出單一 Markdown 檔，放在 repo 既有慣例的位置。
產出的文件是拿進主流程 /grill-with-docs 的素材——research 餵養思考，不取代思考；也是 wayfinder research ticket 的解析引擎。
resolving-merge-conflictsMODEL-INVOKED以「原始意圖」逐 hunk 解決 merge / rebase 衝突

用途

處理進行中的 git merge 或 rebase 衝突：逐 hunk 解決，方法是追溯衝突雙方的「原始意圖」（commit message、PR、原始 issue），而非挑行保留；最後完成整個合併操作，永不 --abort。

觸發時機

已經處於 merge/rebase 衝突中時使用。

工作流程 / 特色

  • 先看當前合併狀態、git 歷史與衝突檔案。
  • 為每個衝突找 primary sources，理解雙方各自的原始意圖。
  • 逐 hunk 解決：盡量保留雙方意圖；不相容時選符合合併既定目標的一方並記錄取捨；不發明新行為。
  • 找出專案的自動化檢查（typecheck → tests → format）並跑完修好，然後 stage、commit、continue 到底。
獨立於所有流程之外；核心原則是「by intent, not by picking lines」。
setup-matt-pocock-skillsUSER-INVOKED每個 repo 跑一次的前置設定（tracker、標籤、domain 文件布局）

用途

為其他 engineering skills 建立三項配置：issue tracker（GitHub/GitLab/local markdown/其他）、triage 標籤字彙、domain 文件布局（CONTEXT.md 與 ADR 放哪、怎麼讀）。

觸發時機

第一次使用 engineering skills 前手動執行；其他 skill 偵測到 docs/agents/issue-tracker.md 不存在時會提示使用者回來跑它。

工作流程 / 特色

  • 是「prompt-driven skill」而非腳本：先探索（git remote、CLAUDE.md/AGENTS.md、monorepo 訊號等）→ 呈現發現 → 逐節確認 → 才寫入。
  • 產出 docs/agents/issue-tracker.md、docs/agents/triage-labels.md、docs/agents/domain.md，並在既有的 CLAUDE.md 或 AGENTS.md 加入 ## Agent skills 區塊。
  • 每節都帶推薦答案讓使用者一句話接受；探索已能決定的節直接跳過。
絕不複製或另建 AGENTS.md/CLAUDE.md；已存在的 ## Agent skills 區塊就地更新而非重複附加。
tddMODEL-INVOKED測試驅動開發的參考紀律：紅→綠迴圈與 seam 選擇

用途

測試驅動開發的參考紀律：紅→綠迴圈、什麼是好測試、測試該落在哪些 seam、反模式清單。讓 red-green 迴圈產出「值得留的測試」，以垂直切片一次建一個行為。

觸發時機

使用者想 test-first 建功能或修 bug、提到「red-green-refactor」或整合測試；也被 /implement 內部驅動。

工作流程 / 特色

  • 只在 pre-agreed seams 寫測試——動手前先寫下要測的 seams 並與使用者確認。
  • 三大反模式：implementation-coupled（重構就壞）、tautological（斷言與實作同源）、horizontal slicing；改用垂直切片：一個測試 → 一個實作 → 重複（tracer bullet）。
  • 迴圈規則：red before green、一次一片、refactor 不屬於迴圈（留給 code-review 階段）。
  • 附 tests.md（範例）與 mocking.md（mock 準則）。
測試讀起來要像規格、跨過 public interface 驗證行為，重構後不該需要改測試。
to-specUSER-INVOKED把對話內容綜合成 spec 並發佈到 issue tracker（不訪談）

用途

把目前的對話內容直接綜合成一份 spec 並發佈到 issue tracker——明確「不訪談」，只整理已討論過的東西。產出的 spec 會標上 ready-for-agent 標籤，不再需要分診。

觸發時機

多 session 的建置工作，在 grilling 完、想法已清晰之後手動觸發，作為 /to-tickets 的前一步。

工作流程 / 特色

  • 先探索 repo，全程使用 CONTEXT.md 的領域詞彙並尊重相關 ADR。
  • 先草擬測試 seams（優先重用既有 seam、盡量用最高層 seam、理想數量是一個），並與使用者確認。
  • 依固定模板寫 spec：Problem Statement、Solution、User Stories、Implementation Decisions、Testing Decisions、Out of Scope、Further Notes。
  • 不含檔案路徑與程式碼片段（會過時）。
to-ticketsUSER-INVOKED把 spec 拆成 tracer-bullet 垂直切片 tickets

用途

把計畫、spec 或對話拆成一組「tracer-bullet」垂直切片 ticket，每張宣告自己的 blocking edges（被哪些 ticket 擋住），發佈到已設定的 tracker。

觸發時機

spec 完成後、要拆成可逐張執行的工作單時手動觸發。

工作流程 / 特色

  • 每張 ticket 是窄而完整的垂直切片（schema、API、UI、tests 全切過），單獨可 demo、大小以一個 fresh context window 能裝下為準。
  • 每張宣告 blocking edges；無 blocker 的立即可做，依「frontier」推進。
  • Wide refactor（blast radius 遍及全庫）是垂直切片的例外，改用 expand–contract 序列。
  • 先把拆分方案以編號清單「quiz」使用者，迭代到批准才發佈；發佈時套用 ready-for-agent 標籤。
「Make the change easy, then make the easy change」——先找 prefactor 機會；每張 ticket 自包含，做完即可丟棄其 context。
triageUSER-INVOKED把 issue tracker 的進件推進小型狀態機，產出 agent-ready 任務簡報

用途

把 issue tracker 上的 issue（以及被視為請求管道的外部 PR）推進一個小型狀態機：分類、驗證、必要時 grilling、產出 agent-ready 的任務簡報（agent brief）。只處理「不是你建立的」原始進件。

觸發時機

維護者手動執行 /triage，用自然語言下指令，如「show me anything that needs my attention」、「move #42 to ready-for-agent」。

工作流程 / 特色

  • 兩個 category 角色（bug、enhancement）+ 五個 state 角色（needs-triage、needs-info、ready-for-agent、ready-for-human、wontfix）。
  • 每則貼到 tracker 的留言必須以 > *This was generated by AI during triage.* 開頭。
  • 分診時做兩項 codebase 檢查：redundancy（是否已實作）與 prior rejection（查 .out-of-scope/ 知識庫）。
  • 先驗證主張（重現 bug、checkout PR 跑測試）再 grilling；被拒絕的 enhancement 寫入 .out-of-scope/ 知識庫。
/to-tickets 產生的 ticket 已是 agent-ready，不要再分診；標籤字串可透過 /setup-matt-pocock-skills 客製對應。
wayfinderUSER-INVOKED為超大模糊工程在 issue tracker 上畫出一張共享決策地圖

用途

為「大到一個 agent session 裝不下、且路徑還埋在霧裡」的工程（greenfield 專案、巨大 feature）在 issue tracker 上畫出一張共享地圖：地圖是一個 issue，下面的「decision tickets」一張一張解決，直到通往目的地的路清晰為止。產出的是決策而非交付物。

觸發時機

面對超大、模糊、跨多 session 的工作時手動觸發；範圍明確的 feature 不該用它（太慢太重）。地圖清空後移交給 /to-spec 走主流程。

工作流程 / 特色

  • 地圖 = 一個標記 wayfinder:map 的 issue，內含 Destination、Notes、Decisions so far、Not yet specified（fog of war）、Out of scope。
  • Ticket 分四型：research（AFK）、prototype、grilling、task；分 HITL 與 AFK，claim 方式是 assign 給自己。
  • 用 tracker 原生 blocking 關係渲染 frontier（open + unblocked + unclaimed）。
  • 兩種模式：Chart the map（命名目的地 → 廣度優先 grilling 畫霧 → 建地圖與 tickets）與 Work through the map（每 session 只解一張 ticket）。
「Plan, don't do」——想直接動手做通常代表已到地圖邊界、該移交了；地圖刻意不完整（fog of war）。
wizardMODEL-INVOKED產生互動式 bash wizard，帶人類完成只有人能做的程序

用途

產生一支互動式 bash wizard，一步一步帶著人類完成只有人能做的程序：開通基礎設施、設定憑證或 CI secrets、操作陌生的第三方 dashboard、執行一次性 migration/cutover。它負責開 URL、說明點哪裡、捕捉值、寫進 .env 和 GitHub secrets。

觸發時機
